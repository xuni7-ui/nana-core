## 缺陷：OBSERVE → seen 先入账 → 后续 ACT 无法再处理同一条事件

### 现象
B站靶子事件 `at:1:316348739601`（BV18YHf63EyC，正文「@涟奈子也 奈奈，帮我看看这个视频讲了什么？」）
到达时，事件泵那一拍跑在 **observe（空跑）** 档：

- 08:27:02 该 eid 进 `seen`，status=`inflight`
- 当拍 Agent 以 `dry=True` 空跑 → `agent_status=DRY_RUN`，`sent=false`，`rpid=null`
- 落盘 status=`OBSERVED_DRY`，`core_status=DRY_RUN`，reason=「空跑：未发送、未写账」

之后即使把 mode 切到 `act`，该 eid 已在 `seen` 里 → `new=0` → **再也进不了 Agent**。

### 根因
`run_once()` 的次序是「**先入账、再按 mode 决定 dry**」：

```
new = [e for e in events if e["eid"] not in st["seen"]]
  → _mark(st, ev, "inflight") + save_state()      # observe 与 act 都会写
  → dry = (mode != "act") 空跑                     # observe 到此为止，但账已入
```

这个次序是 C.4 的**故意设计**（保证「同一事件最多进 Agent 一次」，防轮询重复触发重复发送），
但它没有区分「这一次只是空跑偷看」和「这一次是真的处理完了」——空跑也占了去重名额。

### 影响面
- 只影响 **observe 拍吃掉、之后才切 act** 的场景。
- 正常情况下「先切 act、再来事件」不受影响（08:35 的真实闭环就是证明）。
- 不造成误发、不造成重复发送；后果是**事件被空跑吞掉，需要人工把该 eid 退回未处理**。
