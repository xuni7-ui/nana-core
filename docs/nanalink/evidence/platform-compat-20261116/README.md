### Original watch source withdrawal closure

The governed `BilibiliReadPort.execute` previously captured the video reading without its chosen original source as a Memory parent. The original C → Manager/Grant/Kernel → owned Bilibili HTTP fixture reproduced a real source-dependency failure: after withdrawing the source that authorized the watch, its video reading and sampled frames remained readable. The candidate rechecks the original bound C/source after I/O and captures the resulting reading with that original source as a parent. Existing Memory dependency closure now removes the reading and frame experiences when the source is withdrawn. Independently sourced readings of identical video content remain distinct; withdrawing one parent leaves the other current. If withdrawal happens during the synthetic fetch, no reading or frame is retained, the action stays `UNKNOWN`, and repeated dispatch does not refetch; the original API reports `ACTION_PAYLOAD_SOURCE_NOT_CURRENT` because its governed payload is withdrawn. This is not a real Bilibili account test and it does not resolve platform-side unfollow/delete notification discovery.
