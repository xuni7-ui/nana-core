# NanaLink synthetic platform transport isolation

C-owned transport/workflow compatibility fixes on A `35740e7f2f518b9b2607bbd952759aa80683cf4c`. The Bilibili account transport previously allowed `SYNTHETIC_LOOPBACK` with no loopback endpoint, which created a normal remote opener; the original account workflow treated the synthetic realm as eligible for its isolated fixture path. The constructor now requires the synthetic realm and an explicit literal loopback endpoint together, and the original account workflow revalidates the opener type and loopback endpoint at its authority boundary. Other realms continue to reject an injected loopback endpoint.

The standalone QQ official adapter also accepted `SYNTHETIC_LOOPBACK` with the real official URL and trusted mutable endpoint/realm state after construction. It now requires an explicit literal HTTP loopback endpoint for synthetic mode and rechecks endpoint/realm before each API request. Non-synthetic mode remains pinned to the official API. Neither change provides a Grant, logs credentials, sends a message, or modifies an original Store.

Local tests reproduced both constructor gaps and test post-construction endpoint/opener mutation without making external requests. Combined official adapter, private dynamic source, notifications and original Bilibili account/runtime tests: 57 passed in 17.20 seconds; related Bilibili/platform runtime group before the final focused revalidation: 66 passed, with both focused checks rerun afterwards. Actual account login, external sends and production remain untested. The original public Bilibili reader has its own synthetic-origin constructor and A-owned S5 consumer; its original Kernel boundary already verifies a literal loopback opener, but standalone constructor consistency is a separate A handoff, not claimed fixed here. Revert the two transport/workflow changes and focused tests to restore previous behavior; no persistent schema is changed.
