# QQ connector disable: queued event handoff

C-owned increment on A `35740e7f2f518b9b2607bbd952759aa80683cf4c`. A QQ event could be admitted to the existing bounded unified transport, then its connector disabled before the transport drained. The existing forward path did not recheck the connector state and could still hand the event metadata to Core. The sidecar now checks the owning connector immediately before initiating the existing Core forward; if disabled, it returns a `CANCELLED` receipt, records a body-free status, and does not auto-retry. Another account's queue remains independent.

The controlled two-account test enqueues one event per account, disables the first, drains both and verifies that no Core-forward call occurs for the disabled account while the other account proceeds to the original UNKNOWN metadata receipt. Before the fix the first was forwarded. OneBot HTTP/WS/reverse-WS, management, bounded transport and official QQ tests: 39 passed in 3.59 seconds. Fixtures are local and synthetic; no real QQ or external message was used. A forward already handed to its worker before disable cannot be recalled by this check, and existing Core authority remains responsible for any independently admitted work. This changes no schema, Grant, account binding or social-send retry; revert `src/nana_core/nanalink/sidecar.py` and the focused test to restore previous behavior.

A further controlled HTTP management test reproduced a disable-then-reenable case where old entries stayed in the adapter or unified queue. The actual disable endpoint now removes that account’s still-queued entries from both bounded queues, reports a cancellation count, and keeps dedupe records; a separate test checks another account’s queue survives. The local HTTP management/OneBot/transport/official suite passed 40 tests in 3.80 seconds, followed by the independent cross-account cancellation test. This cancellation does not recall an already-started worker or erase independently admitted Core work.

The existing official adapter also retained volatile captured message bodies, reply anchors and account-preflight state after management disable. A local official-shaped account fixture reproduced the residue. Explicit host management disable now clears that account’s in-memory official capture, anchors and preflight state after cancelling pending queues; re-enable cannot read the old capture. This does not delete original Core memory or affect another account. Official/OneBot management, network and transport tests: 42 passed in 3.60 seconds. No new SDK hook is required for rollback versions. Cleanup covers the bundled official adapter’s known fields; independently supplied adapters and any additional volatile state have not been qualified.
