# Bilibili notification capability and consent

C-owned adapter projection on A `35740e7f2f518b9b2607bbd952759aa80683cf4c`. The existing `notification.reply` capability reported available whenever general reading was authorized, even though the actual C.4 notification adapter additionally requires an enabled channel and private-read authorization. It now projects those existing conditions and returns a non-sensitive unavailable reason. This is a capability/configuration indication, not proof that an account is logged in, a notification was received, or a platform action succeeded. The existing event and permission contracts are unchanged.

An isolated adapter test first reproduced the incorrect available value with private-read disabled, then checked enabled/disabled and authorized states. Original Core adapter, private notification and source tests: 19 passed in 11.82 seconds. The test uses no account or network call. The existing phone client currently has no localized label for `notification.reply`; product owner B can add a user-facing explanation without changing the Core contract. Revert the projection and focused test to restore the previous behavior; no data or schema migration is involved.

The same projection issue affected Bilibili DM receive and QQ receive/send when channels were disabled or required private reading had not been authorized. Existing QQ wrapper capabilities are now calculated from the current channel flags instead of a one-time tuple; Bilibili DM receive and message-send projection likewise respect their original channel/read prerequisites. A QQ official backend still marks independent readback unavailable. These remain configured capabilities, not proof of account login, a Grant or delivery. QQ/Bilibili wrapper, private source/notification, official and original bridge tests: 45 passed in 18.87 seconds; original incorrect projections were reproduced before the change.
