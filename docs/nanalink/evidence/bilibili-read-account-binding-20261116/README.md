# Bilibili private reads: verified account binding

C-owned compatibility fix based on A `35740e7f2f518b9b2607bbd952759aa80683cf4c` (revision 260), using the original `BilibiliAccountTransport`, source bridge and Store. Previously a private dynamic poll verified the account via `/x/web-interface/nav`, then resolved the credential again for the feed without checking it matched the credential just verified. A credential rotation in that interval could associate another account's feed with the original account. The two private notification pages had the same gap if a credential changed between pages.

The existing in-memory account/cookie attestation is now checked before the private dynamic HTTP request; that feed consumes the attestation. Both private notification pages check that same verified account/cookie, and a mismatch invalidates it. The checks happen before network I/O; they do not store or log credential material, add a second identity or Store, create a Grant, or change an external action. Existing request and original budget reservations remain in place. Reverting `src/nana_core/life/bilibili_account.py` and its focused tests restores prior behavior; no persistent schema is changed.

An owned loopback account/notification server and synthetic credential resolver reproduced both failures on the preceding code. The fixed direct tests reject a changed credential before a feed request, require a new preflight for another dynamic read, and reject a changed credential before the second notification page. An original pump test changes the credential between the account and feed calls: only account verification reaches the local HTTP peer, no private dynamic evidence is stored, and repeating the same reserved poll does not retry. No real accounts, real external sends or paid calls were used. Private source, notification, public video history, original Bilibili account and runtime tests: 47 passed in 17.82 seconds.

This checks the credential used for each individual private HTTP request against the account preflight; it does not prove platform-side unfollow/deletion detection or replace retention consent, canonical activation and original source withdrawal. Bilibili DM and other account paths were not expanded by this increment. Long-running, real-account and production qualifications remain pending.
