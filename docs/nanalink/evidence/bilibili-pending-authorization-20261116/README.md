# Bilibili pending notification authorization

C-owned increment on A `35740e7f2f518b9b2607bbd952759aa80683cf4c`. The original C.4 notification adapter returned previously polled private metadata before checking whether its channel remained authorized. In a controlled owner fixture, revoking private-read authorization on disk still returned the pending item.

On each enabled receive, the existing adapter now checks channel flags and platform authority before releasing any pending notification. For non-synthetic platform transports it reloads the existing configuration and checks that the exact channel and surface binding remain current; an authorization/configuration check failure clears the in-memory pending queue and fails closed. It does not fetch, send, grant or make a model call to check a pending item. The synthetic loopback fixture retains its existing configuration contract, while its channel flags and authority are still checked. Reverting `src/nana_core/nanalink/adapters.py` and the focused test restores the old behavior; no persistent schema is changed.

An isolated owner Store and synthetic configuration test verifies an unchanged authorized configuration releases an already-pending item; after private-read revocation a second pending item is not returned and the queue is empty. The pre-change implementation returned that item. Private notification/source, original Core wrapper and Bilibili runtime tests: 22 passed in 14.65 seconds; the amended focused valid-then-revoke case independently passed. The test uses a local authority stub and makes no real Bilibili request. This covers this adapter's pending queue, not all other Bilibili event consumers, changes at the platform itself, real account behavior or production operation.
