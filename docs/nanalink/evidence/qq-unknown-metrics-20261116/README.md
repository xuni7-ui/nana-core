# QQ transport UNKNOWN accounting

C-owned increment on A `35740e7f2f518b9b2607bbd952759aa80683cf4c`. The original Core receipt already kept uncertain sends UNKNOWN and did not retry; however, a WebSocket disconnect that completed an in-flight RPC with `ONEBOT_COMPLETION_UNKNOWN_NO_RETRY` was not counted in the connector's `unknown` metric. An unusable official ACK similarly left its metric at zero. Operators therefore could not rely on the existing status metric to spot these cases.

The OneBot adapter now counts in-flight timeout/connection/cancellation, explicit lost completion, and unusable write responses once, after a request could have been handed to the transport. The official adapter counts unusable or unreadable POST responses and unusable ACK IDs. Existing protocol rejection and original Kernel receipt/independent verification remain authoritative; this metric also includes uncertain reads, is volatile, and is not a durable or exhaustive count of actual external sends. No send is retried and no new action or authorization is created.

Owned local fixtures reproduced the missing counts: a WebSocket ACK loss with one platform attempt now records one UNKNOWN after reconnect; an oversized write response records one; a complete chunked ACK records zero; an unusable official ACK records one with one POST. OneBot, official QQ, management and original bridge tests: 43 passed in 10.59 seconds, followed by three focused ACK checks. No real QQ account, external send or production observation was used. Revert the two adapter files and focused tests to restore previous metrics behavior; no persistent schema changes.
