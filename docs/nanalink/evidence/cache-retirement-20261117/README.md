# Session cache withdrawal and B handoff

C candidate is stacked on PR #25 `9e76454220067e6f15ab06fe831ae00cb4d539f4`, based on A `4f25b48ab673ed43507c4b7cd058cbeac022f729`. The prior cache could admit a source, observe its callback become false, then read the old handle again when the callback became true. The controlled regression failed on that prior code. Within one cache session the new code remembers observed retirement, rejects old handles and re-admission under that source reference, deletes cached bytes when no other source supports them, preserves independent sources of shared bytes, bounds retirement entries by `max_items * 64`, and fails closed on overflow. Interrupted initial ingestion also retires that reference; an exception from the source check is treated as unavailable and retires an already-admitted reference for the session. A closed cache cannot be reopened. If unlink fails, the file remains tracked for later cleanup.

This is a bounded in-memory cache safeguard, not a second authority or persistent tombstone. It cannot observe withdrawal that occurs entirely between callback checks, and it cannot enforce cross-process retirement by itself. The original MemoryService/Store must keep the authoritative tombstone and issue a new reference for a new authorized source. Cached shared bytes are retained only while another admitted source supports them. The check does not create a Bilibili platform/account/byte attestation, and no real platform account, model call, social send or production action was used.
