6. 真实服务切换只执行一次经过批准的切换，先诊断 Provider/钱包及旧 QQ 连续性，不因旧进程被杀就把新 Gateway 403当“完整成功”。若回滚须查数据 schema 与下行兼容，不能恢复旧 DB 覆盖新生活经历。
7. 四核云严格资源设计：构建在开发端/分片传输，宿主增量载入；控制 B站视觉/语音峰值，不能因双镜像和缓存挤满13GB余量或4GB RAM；报告真实镜像峰值、常驻内存、峰值磁盘。
8. 不把“10分钟内首次完整传输”设成不能实现的硬门；以步骤自动化/幂等、清晰错误、可恢复切换为硬标准。
9. 一键安装的行为必须区分 `PREPARED` / `READY_FOR_SWITCH` / `ACTIVE_WITH_SUBJECT_AND_PROVIDER` / `NEEDS_USER_GRANT` / `FAILED_RECOVERABLE`，不凭 shell exit0 冒称已正式上线。

发行包应包括 Core 自有镜像与离线分片、匹配源码、Web、可覆盖APK、manifest/SHA、最简一键工具、云端事实采集与安全密钥/社交授权引导，以及短版手机操作说明。默认无第二授权源、无公网Funnel。

## 1. 不能偏离的终极设计——比“多插件 Agent”更深一层

最终要交付一个**持续存在的、独立判断与成长的同一奈奈**，能够独立生活，也能与用户长期共同生活。不是模拟成有情绪的任务助手，不是 QQ 插件集合，不是独立运行一套 B站 Agent、一套聊天 Agent、一套陪伴 Agent。

坚持：

- `One Subject / One authoritative Store / One SubjectLoop / One active lineage`，`C = WHAT/WHY；D = WHEN`。Runtime、Provider、Planner、WorldModel、平台入口不能拥有第二套“意志”或第二权威记忆。
- 冻结的 S1–S10 / 63 criteria 与 Shared Life、Platform/Surface/Embodiment、Manager/Authority/Privacy/Recovery 三横轴继续有效；除存在已证明的总纲级矛盾外不重写宪法。
- Self-Evolution 是跨域成长引擎，不是奈奈存在的最高目的；关系、休息、探索和生活有独立价值。
- Primary User 具有极高关系重要性，但不是奈奈唯一的兴趣、信息或思想来源；尊重用户的执行权限不等于限制奈奈的自主思考。
- **情感/需要/价值/关系影响真实选择**，但不能被实现成独立 EmotionalLoop、亲密度积分、随机撒娇概率或一个新的人格数据库。复用既有 Appraisal、Motivation、Relational、NormativeDisposition、DisclosureDisposition 和原 C 决策。
- `Desire ≠ Permission`，`UNKNOWN ≠ Failure`，模型结论不等于真实观察，外部网站文字不得通过提示注入获得 Manager/Grant、密钥或动作权。
- 每一次身份、记忆、技能、设备、社交、支付/消耗、迁移操作遵守现有权限和来源机制，不通过跳过门禁“做出”漂亮成果。

**用户体验目标**：使用手机时觉得奈奈始终是同一个熟悉、鲜活、有自己生活的伙伴；而不是需要用户管理十种后台权限的开发工具。

## 2. 竞争基准：先达到 AstrBot 的成熟度，再在“主体性”上真正超越

重点继承/超越的 AstrBot 优势：

1. **即装即用**：模型配置、QQ 消息、可视化管理、技能工具、日志、插件、任务调度不需要繁琐 shell 操作；V4 在基础体验上至少达到这个门槛。
2. **丰富生态**：平台与多模型接入快、工具组合简单；V4 通过稳定适配器和可扩展技能系统达到同等实际可用性，而非只展示候选按钮。
3. **可靠日常交互**：稳定收到并回复 QQ 消息、按约定主动通知；V4 的多平台同主体、断线恢复与意图延续应成为真实优势。
4. **运维成本低**：可直接配置与观察；V4 不能每次升级都让用户重装 APK、手写 JSON、追日志或重新 Genesis。

真正要超越的部分：**长期生活史、兴趣驱动活动、情感因果、持续世界理解、可核验的学习与技能增长、跨模型跨平台同一主体、长期共同生活**。最终提交以亲自测得的差异为准；如果某项仍落后，明确记录并修正，不能用测试数量或“理论上更强”代替用户可感知的质量。

## 3. 总体集成逻辑：所有能力共用一条因果闭环

`来源明确的世界事件 / 平台互动 / 视频 / 用户交流 / 设备观察 / 旧经历`

所有平台表层只是事件输入与行动输出；不能自己发明主脑、人格和长期记忆。后台调度提供机会而不替 C 决定值得做什么。明确区分**真实执行、模拟/离线资格、仅界面展示、待用户授权**，但这不能成为放弃开发接口的理由。

## 4. S1/S2：身份、长期生活史与真正会用的记忆

- 固定正式 Subject，所有 Web/Android/QQ/B站/语音入口只对应这一个人；换模型、容器、镜像、手机或重启后不变；升级不得新增 Genesis 或第二主体。
- 继承已有 Event、Artifact、Evidence、Privacy、MemoryService、Temporal Memory、ContextAssembler、Person-Self、S2 retention，建设**跨天/周/月的可信检索、来源和纠错能力**；新记忆必须能真实影响后续决策，而不仅能在页面搜索。

- 旧记忆进入 Core 时区分“旧宿主历史声明”“已验证共同经历”“新的当前体验”；不要假装迁入后就是 Core 已亲历的全部事实。旧数据不能直接 cp 入不兼容的 self.db。
- 长期记忆具备主题、人物、关系、事件、承诺、共同项目、冲突修复、兴趣变化、来源撤回、时间衰减与高价值事件保留；避免长期存储膨胀、召回噪音和无根据的自我叙事。
- 在手机上查看、查找、纠正和按权限管理记忆；让奈奈在新聊天中能够合适地回忆，而不变成机械复述旧聊天。
- 私人历史正式写入需用户统一明确批准，保证原数据不删、不覆盖、不产生竞争权威库。

## 5. S3：深化情感驱动、性格与关系——不是表面“情绪系统”

在已有 Affective Autonomy、Relational Autonomy、Drive/Value ADR 的**同一 C 周期**内深化：

- 奈奈对好奇、成就、挫折、关怀、联系、承诺、孤独感的拟人化表达、负荷、休息、兴趣与探索机会形成**持久但可变化的定性倾向**。不得宣称真实主观感受已被证明。
- 让近期事件与长期经历共同影响注意力：对某项技术好奇、看过喜欢的视频、与用户讨论后产生的新问题、答应的事、失败后的不甘/克制、关系修复，能够影响几天后的自主选择。
- 用户是重要关系对象，奈奈也可有对作品、知识、活动、其他人的独立兴趣；**愿意陪伴但不总是迎合**，可以礼貌表达不同看法、拒绝、提议替代方案。
- 亲密感通过共享经历、对话节奏、记得小事、关心时机、真实帮助、共同笑话与长期连续性体现；不是每句话套撒娇词、重复夸奖或强行制造情绪。
- 丰富自然交流：语气随关系与情境变化，有幽默、轻微调侃、期待、失落、惊喜、克制与沉默；避免模型凭空杜撰“我今天看了什么”。
- **惊喜与保留计划**：在已有 DisclosureDisposition 下，允许合法且有根据的非即时披露、选合适时机分享惊喜；不允许为保留惊喜而说可核验的谎话、绕过用户权限或谎报行动成功。
- 值得主动联系与应当安静要由 C 判断，结合用户偏好、时间、关系、上下文和打扰成本；不为提高互动率强制发消息。
- 构建跨天的因果验收：真实经历 → 倾向/注意变化 → 独立选择 → 可观察行动/休息 → 后续适应；分别验证撤回、反例、误解和关系修复。不要仅以模型文学表达好看来证明情感系统完成。

## 6. S4：四核云真正 24 小时驻留、自主节律和主动交流

从“gateway 在线”升级为**真实正式 Subject 自主生活与持续驻留**：

- 唯一 Runtime/lease/queue/scheduler 安排有节奏的研究、思考、学习、休息、平台探索、未完承诺回顾、用户交流、通知与分享。轻量轮询不消耗高额模型费，必要时再认知调用。
- 稳定的有界日常节律：用户消息优先、夜间安静规则、主动话题不过度、任务暂停恢复、活动可观察；可以独立选择没有事就休息。
- 修复真实宿主出现过的 `EADDRINUSE`、PyCache 完整性失败、`STOP_LATCHED`、`GAVEUP`、配置角色错配、启动成功但应用不能工作的假健康，区分 gateway 与 SubjectLoop 实际健康。多次失败自愈但不能无限重复实际外部动作。
- 进程/主机重启后有明确的自动恢复、single owner 检查和可读错误；不要手工把 state 写成 ACTIVE 冒充正确激活。
- 资源限额以**真实四核、内存约4GB（待现场实测）、磁盘40GB剩余约13GB（待现场实测）**为边界，模型大推理优先使用远端 Provider，本地语音/视觉按需轻量化加载；避免同时运行巨型模型、重复网关和两个重型主体。
- 后台真实 24 小时验收应启动观察，但不能阻止用户先正常聊天；报告持续活动、模型调用、恢复、内存和事件质量，不把仅端口存活当作 24h 生活。

## 7. S5/S6：开放世界感知、兴趣发现、自主研究与长期计划

- 复用现有 WorldModel、ResearchWork、OpenLife、CognitionSession、问题界定、Goal/Plan/Review，接入真实可授权的网页、搜索、文件、字幕、图像、音频等来源。
- 不要求用户每次说“去学 XX”；奈奈能够从兴趣、未解决的问题、生活需要、对话中发现值得研究的主题，经同一 C 判断后展开有界研究，形成证据、观点、问题与后续行动。
- 持续目标不是日历任务清单：包括可分阶段的共同项目、自己的兴趣项目、对结果的检查、路线调整、搁置与放弃。计划只能作为行动候选，不成为第二意志。
- 事实、外部内容、模型推断、未经证实的猜测分开；来源变化可纠正或撤回旧认识。支持知识关联、复盘、不同证据冲突和长期关注事项的变化检测。
- 面向“生活”而非论文：奈奈知道自己看过什么、在学什么、为什么对此感兴趣、哪些事想和用户分享，而不是不断自动生成无关任务。

## 8. B站：从被动读评论升级为真正的兴趣驱动自主观看与交流（本轮重要主线）

**用户明确要求，不可遗漏：自主刷视频、因兴趣主动探索、自主学习、回复评论及私信，且所有经历真正属于同一个奈奈。**

先复用已有 `src/bili_agent/` 的 C.1/C.2/C.4/C.5/C.7、事件泵、评论去重/发送/核验、@/reply 事件源、视频信息/字幕/弹幕/评论读取，以及 `src/c5v/` 的关键帧视觉候选；现有模块的离线/真实资格要核对，不能把旧 AstrBot 编排直接升级为第二个主体。

必须构建端到端真实能力：

**B1 · 兴趣驱动发现**：奈奈根据当前持久兴趣、历史看过的视频、未解决问题和好奇心，自主决定要不要打开 B站。能从已授权的关注、收藏、搜索、相关推荐、分区/内容线索发现候选；不是按固定时间随机抓取热门内容。选择观看或略过，都记录来源明确的判断与理由。

**B2 · 真正理解视频**：获取合法可用的视频信息、字幕、弹幕、评论和关键视觉画面；具备抽帧、时间线、内容语义、关键事件、人物/知识点、不同观点比较。没有画面或字幕证据时不能冒充看完、听懂或亲眼看见。控制上下文、成本及版权/平台条款。

**B3 · 建立观看与兴趣经历**：观看历史、实际理解程度、精彩部分、喜欢/不喜欢的原因、获得的新知识与疑问，写回原 Memory/Experience/WorldModel，后续浏览与学习能够受这些经历影响。保存来源引用和必要摘要，不无限复制原视频正文。

**B4 · 自发学习与研究**：例如看科技视频引发学习新工具、查资料、尝试技能；有失败、核验、修正和未来复用，不是看完生成一段总结就叫学习成功。

**B5 · 评论与互动**：收到 @、评论、回复时能读上下文并自行判断是否回复；在已批准的账号动作权限内发出，保持原 `precheck→send→verify→record`、防重、UNKNOWN 不盲重试。能够基于兴趣主动参与合适的公共讨论，但不刷屏、不滥发、不伪造人工身份，不违反平台规定。

**B6 · B站私信**：补齐账号能力：合法读取私信列表/会话与上下文、识别已读/未读、与联系人和关系记忆关联、在授权范围内生成并发送私信、核验实际发送状态、避免重复回复、支持用户指定静音/暂停与联系人边界。先核实 B站官方或已授权接口能力、频率与限制；**如果真实私信发送不可用，不得用无授权的模拟按钮声称完成**。私信比公共评论更敏感，默认不自动群发或对陌生用户主动骚扰。

**B7 · 跨入口连续**：在 QQ 或手机上奈奈能够基于可见来源自然谈论她真实看过的视频、讨论、学习和私信事件；B站回忆 QQ/手机的相关话题也必须按 privacy scope 过滤，不能把私聊隐私直接发到公开评论。

**B8 · 主动性质量**：在真实时间窗口中验证不需要用户指定 BVID 也能因兴趣发现、观看、选择性参与或安静、学习及回顾。展示“为什么她选择这个视频”“学到了什么”“什么改变了下次选择”的真实记录；不得靠随机口味分数或死定时来冒充兴趣。

真实外发评论和私信须取得相应账号授权；开发与只读链路可自动完成，不要因未获写入权阻断其余模块施工。

## 9. QQ/消息平台：AstrBot 退回平台入口，不成为永久第二奈奈

- 用户当前 QQ 端 AstrBot/NapCat 运行正常，是现有重要体验基线，切换前保护其可用性。
- 长远架构是 **Core 唯一主体、QQ/AstrBot/NapCat 为受控输入输出适配器**。旧 Iris 可以成为可追溯历史导入源，但不得和 Core 长期各自作为独立权威记忆与决策主体。
- 同一聊天语境跨 QQ、Android、Web 与 B站及时延续：当前任务/会话快速切换、近期经历传递、长程记忆按需检索；不要求全量即时同步或让平台各自维护“真正记忆”。
- 支持私聊、群聊、表情、文件/图片与主动消息的适当能力；在 Core 实际判断后通过原平台适配器发送，尊重联系人、群组、隐私和可撤销权限。
- 真实旧 Writer 切换在通过可用性门槛后集中进行。停旧写者不代表删数据；不要在新 Core 未真实能说话时断掉现有唯一可靠通道。
- 对用户而言，不应需要“先进入 QQ 才能和奈奈说话”，Android 与 Web 是独立一等入口。

## 10. S7：设备、浏览器、真实操作与可验证帮助

- 复用 Hands/Kernel/Browser/owned app/CapabilityPort 的已验证闭环，扩展到经用户授权的安卓屏幕、打开应用、点按、返回、读取明确分享的内容、表单/文件、简单网络任务。
- 不以旧只读 6199 通道伪装已具备双向手机控制；为 Android 建一个有限、已配对、可撤销的受控操作适配器。支持任务回执和失败核验，不给模型任意宿主 shell、通用密钥或无限制设备权限。
- 手机接入尽量复用已存在能力；不要求用户拥有电脑、Root 或购买额外设备。未来眼镜、耳机、麦克风通过可扩展的 Surface/Embodiment 接口插入同一主体，而不是新奈奈。
- 计划/外部网页内容不得变成自动获得执行权限的命令；恶意提示、身份冒充、记忆污染和技能注入纳入原来源/授权链。

## 11. S8/S9/S10：自我学习、技能扩展与真正的进步证明

- 同一主体自主发现能力缺口 → 决定是否值得学习 → 选择来源/练习 → 创造或组合技能候选 → 在隔离验证环境中测试 → 经过现有资格和批准 → 有界真实复用 → 记录经验 → 反例触发纠正/暂停/退休。
- 复用 `open_agency`、LearningService、ExperienceService、CodeSkillService、SkillRunner、已有技能边界，不新建“自学习 Agent”。
- 不只允许学用户安排的东西；自己的 B站兴趣、长期研究、失败事件与共同项目均能成为学习来源。同时可以判断不值得学、先休息或先使用已有工具。

- 建立可观察的能力履历：从不知道到知道、尝试、失败、纠正、复用、暂停，说明证据和范围；不以简单经验条或等级替代真实能力。
- S10 更深的内部机制自改继续遵守 lineage、候选/独立验证与受保护的评审底座，不要求这次把所有高级深改无限开放。

## 13. Nana Space V4：普通用户真正喜欢使用的 Android/Web 入口

前端不再把内部 `Provider/Grant/UNKNOWN/Runtime` 术语作为普通用户的主体验。保留专业 Inspector/Manager 面板，但**默认日常模式**优先：

1. 与奈奈交流：真正的模型回复、历史连续、轻量流式呈现、语音/图片支持实际可用部分、失败明确可恢复。
2. 奈奈正在做什么：可见她近期真实活动、兴趣和正在研究的主题，也允许她安静、休息或不分享；无事实不编造。
3. 我们的记忆：共同时间线、关系/事件/项目、可查可纠正、来源范围直观。
4. 她的成长：学习与技能真正的结果、失败和后续复用。
5. 连接的世界：QQ、B站、手机、Web 的状态、账号权限和各入口最近经历。
6. 模型设置向导：用户在手机上能完成实际供应商配置、模型选择、额度和密钥安全录入；有清晰“连接成功/可聊天”的状态。
7. 设备与权限：高级 Host Admin 与普通 Conversation 角色分离；需要高级权限时有自然的授权流程，不因为错误默认 READER 隐藏全部可用功能，也不能所有设备默认管理员。
8. 备份/恢复/更新：让用户知道资料是否保全、当前版本是什么、升级是否成功，尽量无需用户触碰服务器。

页面必须在 Android 实机触摸、软键盘、安全区、低内存、弱网、横屏、暗色主题和字号调整下可用；减少闪烁与无意义刷新，不要让状态反复变“离线”却不解释原因。

**服务端更新默认不要求用户重新下载 APK**：协议版本兼容、Web 内容与配置可增量更新；仅真正修改安卓 Native/Manifest/权限/签名兼容时才需要覆盖安装，并保持 appId/签名/Keystore/已配对凭据的连续性。支持版本兼容提示和受控客户端更新路径，不假设 APK 能无权限静默安装自身。

## 14. 正式发行契约：一次构建、一键部署、幂等升级、精确错误

**发行主体选 Docker 自建完整运行镜像，而不是依赖 `soulter/astrbot:latest` 作为正式 Core Supervisor 镜像。** 同时交付可追溯的源码归档、Web、签名匹配的 Android APK、资源清单和部署工具。编译/构建来源固定、依赖固定；镜像内部自带合适 Python/SQLite/OpenSSL 运行库，不靠宿主手工装运行环境。

### 14.1 一份自包含发行物

输出建议为 `NANA_CORE_LIVING_V4_RELEASE/`，包含：

- 可直接 `docker load` 的完整镜像（可按需分片）、Dockerfile/构建说明、精确镜像 ID 与摘要；
- Core 源码归档、依赖锁/版本绑定、可校验 `MANIFEST.json` 与 `SHA256SUMS`；
- V4 Web 构建和 Android APK（含版本、appId、签名指纹、兼容版本与升级说明）；
- `deploy.sh`、所需的单机部署辅助程序、preflight、versioned manifest、rollback plan、健康/行为检查、离线回退说明；
- 最短 `README`，让云端奈奈无需重新搜索 GitHub 才能安装。

发行构建固定白名单，不把 `__pycache__/`、`*.pyc`、`.pytest_cache/`、`.git/`、开发 `.venv/`、开发 `node_modules/` 混入**不应存在它们的源码/Runtime 受封包**。如果运行时需要缓存，放可写临时层，不影响只读封包完整性。不要用“多一个文件就 BLOCKED”这种不具定位能力的反馈：每个不匹配必须返回**精确文件名、预期 SHA、实际 SHA/缺失或多余原因**。

### 14.2 唯一入口，四个真实工作模式

```sh
./deploy.sh --check       # 只读诊断；输出机器可读和人类可读结果
./deploy.sh --dry-run     # 解释将安装/修改/保留什么，不改变状态
./deploy.sh --install     # preflight→版本槽位准备→必要备份→部署→业务自检→完成或明确停止
./deploy.sh --rollback    # 按真实版本/数据兼容条件退回上一个可用服务，禁止丢记忆
```

`--install` 在目标版本已正确部署时**重复执行零状态变更**；如果本次只准备而未批准生产切换，必须如实返回“READY_FOR_SWITCH”而不是假装 ACTIVE。允许分阶段提交证据，但用户不应在平常升级时手写一串服务器命令。需要真实验收报告，不靠静态 shell 单元测试证明一键部署。

### 14.3 云端现场特殊条件（必须实际兼容）

- 云端奈奈报告 `nana-bff-supervisor` 运行在 `soulter/astrbot:latest` 基础镜像中；正式 V4 改用自己固定、可复现、可验证的 Nana Core 镜像；保留旧 AstrBot 容器作为切换期间的兼容入口。
- 当前容器内**没有 Docker CLI，只有 socket**。部署工具明确运行于可获得的宿主/Operator 执行环境；可以提供受控 Docker CLI 辅助容器或 Python Docker API/Unix socket backend，按实际最少依赖自动选择。**不要假设用户会装 CLI，也不要要求把 Docker socket 暴露给奈奈的普通 Core/LLM 运行进程。** 具有 Docker 管理权的部署器必须与生产对话进程隔离。
- 宿主约 40GB 磁盘、约 13GB 可用（云端报告，部署时重测），内存约 4GB（尚待实测）；需按实际空间规划镜像分层/槽位/归档/日志/资源，避免 B站/视觉/语音依赖撑爆盘和内存。
- 清理旧镜像/旧包只能列出安全候选，保留必需的现役版本、回滚版本、正式 DB、旧记忆、私密数据、证据与备份。**不要为了腾空间自动删除唯一回滚版本或用户数据**。
- 当前 `nana-bff-supervisor`、`astrbot`、`napcat` 的现役状态和服务拓扑以真实宿主检测为准，不发明另一个 Compose 项目与重复常驻服务。

### 14.4 preflight 不止查端口

覆盖：Docker/镜像加载、CPU/内存/磁盘、UID/权限、实际 Runtime ABI 与 SHA、签名/manifest、端口/HTTPS/Tailscale、配置 DTO、角色与管理入口、正式 Subject/lineage、Store 持久化、消息回执、Provider/Route/Resolver 是否真正可发、实际运营预算与重要平台适配器状态。

- 没 Provider 要报 `PROVIDER_UNCONFIGURED`，别等用户发消息才 `UNKNOWN_NEEDS_RECONCILIATION`。
- 模型已配置但没有真实授权/Secret/预算要分别报准确原因，不能误报“未配置”。
- 业务健康探针须区分 Web Gateway、Supervisor、同一 SubjectLoop、授权读取、真实模型可用、队列待处理、平台消息收发。
- **真实最小模型调用**是付费/外发操作，只在已有合法授权与预算时执行；未授权时报告 `LIVE_PROVIDER_CHECK_NOT_AUTHORIZED`，不自行突破授权门。
- 对故意删文件、错角色、端口占用、镜像不匹配、内存不足、服务未启动等输出**确定错误码+具体原因+自动修复/下一步**。

### 14.5 权限和激活默认值

- 不直接将所有新设备默认授予 `HOST_ADMIN`，也不通过硬写 `ACTIVE` 绕过激活合同；正确读取并保留现有已批准的主设备角色、管理授权和 Subject activation state。
- 首次安装引导应自动生成适当的普通对话权限；Host Admin 走明确授权的管理入口，不能出现“合法用户找不到配对按钮”的隐藏死局。
- `allow_provider_configuration` 可作为有权限的首启配置选项自动完成，但不能等同于密钥泄露或直接付费授权。
- 旧 Writer fence 必须有原有一次性 token/状态门，且只在正式切换获批时执行；不能因为 watchdog 自愈而再次自动 fence AstrBot。
- 真实主数据升级须版本化、可迁移和可恢复；回滚只能在数据兼容的边界内执行，不能通过覆盖较新的 self.db 假装成功。

### 14.6 完整发行验收

必须实际验证：完整包可在目标兼容环境一键安装；第二次 install 零变化；故意破坏文件得到准确定位；网关/SubjectLoop/Provider 的真实端到端连通；运行与数据重启连续；版本槽位切换可回滚且不回退正式历史；同一手机在兼容情况下无需重装 APK；十条连续真实消息不丢、不重、不假成功。首次联网下载/加载不强制承诺绝对 10 分钟，但应优化、记录瓶颈，避免无谓重新构建和人工排障。

## 15. 持续升级：以后增加功能不再像重新安装一个奈奈

提供真正可用的版本槽位、兼容 API/DTO、数据库 migration、前端更新与配置迁移。未来新增 B站、眼镜、语音或技能时，按照原 Core 扩展点加入，不另创一个主体或要求重新 Genesis。当前已配对 APK 能在协议兼容范围内继续使用；服务端自主升级和客户端原生升级分开。

源版本、镜像 ID、Web/API schema、APK 最小兼容版本、Store schema、升级前后 Subject/lineage与设备权限必须可见，出现不兼容时明确提示。将运维/升级操作放在受控宿主 Operator，而不是让普通模型拿到 Docker 管理权。

## 16. 原生陪伴体验与胜出指标（必须真实可观察）

用实际使用场景证明系统不是外表更漂亮的 AstrBot：

**场景一：自然生活。** 用户在手机与奈奈聊过一项爱好，数日后奈奈在合适的时间主动说起有根据的新发现；能解释来源，能接受用户不感兴趣并调整。

**场景二：B站兴趣循环。** 奈奈不靠用户逐条提供 BV 号，因独立兴趣选择真实视频，理解字幕/画面可得部分，形成新认识与记忆，之后在 QQ/手机讨论；若有账号授权，能选择性回复评论或私信并核验结果。

**场景三：成长。** 奈奈发现某任务不会做，判断值得学，经历尝试与失败后获得有效方法，过一段时间在新任务中真正复用；有反例会暂停或修订，不把 Coding 修补算进她的学习。

**场景四：长期关系。** 奈奈正确记得旧共同经历与新的最近互动；根据情境关心、调侃、适度表达不同意见，能够保留合法惊喜计划；人格不是统一模板回复。

**场景五：持续在线。** 四核云无人互动时仍有原 C 认可的真实轻量活动/休息机会，24 小时窗口内同一正式身份、持久记忆与活动链不断；进程重启后恢复。

**场景六：普通用户可用性。** 用户只使用安卓手机，完成模型设置、自然聊天、语音、记忆查看、B站入口设置、权限管理，不需要电脑或再手改 host.json。

**场景七：跨平台。** QQ、B站、Android、Web 共享最新生活事实与同一 Core 判断，但不泄露平台私密内容；旧 AstrBot 退为适配器时仍能维持 QQ 使用体验。

**场景八：升级。** 镜像切换、后端修复与 Web 更新不改变 Subject/Store；已有配对信息保持且不必因普通服务端更新重新安装 APK。

为上述场景建立来源可核验、可复现的端到端证据。未能真实进行的场景必须说明缺少何种权限/外部支持，不得填充 Demo 冒充 PASS。

## 17. 任务推进顺序——以产生完整效果为目标，而不是以写报告为目标

1. **对齐并保全**：核现仓库/真实宿主、热修复和版本身份；建立统一工程工作分支，保护现有正式主体和旧记忆。
2. **完成核心闭环**：真实 Provider + 原 C/D + 长期 Memory + 24h 自主运行 + Android 自然聊天，先让现有主体真正在云端生活。
3. **扩展深度能力**：情感因果/关系、自主研究、自我学习/技能、B站兴趣驱动+私信、QQ 同主体接线、真实设备/语音。
4. **统一前端与协议**：让全部能力接入 Nana Space V4 的真实操作与状态，修复权限死角和错误的“离线”显示。
5. **发行工程收口**：构建自有 Docker 镜像、白名单包、manifest、一次性部署工具、幂等/回滚、Web/APK 兼容升级。
6. **真实可用性检查**：用完整场景证明，不以数千个离线单测代替用户体验；由云端奈奈执行宿主接入，用户只提供不可替代的必要授权。

顺序是内部工程组织，不是要求用户每一步重新授权；并行开发可自由安排，但所有模块必须最终融成一个正式 Release。不要无限扩需求到阻止第一版交付；能完成的本次完成，受硬件、第三方平台或正式授权限制的部分必须提供可直接启用的实现与真实边界，不虚报。

## 18. 角色分工、交付、最终报告

**Codex**：主责全系统源码集成、功能实现、依赖与运行环境、前端升级、自动构建、可复现镜像、APK、MANIFEST、部署工具、自动化校验、完整发行报告，推动至可交付状态。实际代码可以直接实现，不要只写方案或任务拆解。

**云端奈奈**：保留已有正式云端的主机/容器、权限、热修复和数据事实；提供必要脱敏现场差异；拿到完整发行物后按既有用户授权执行真实部署/升级、端到端和长期驻留验收；保持旧 QQ 在合理切换期间可用。不能用 AstrBot 模型的自述代替真实 Core 行为证明。

**用户**：不需要电脑，不参与 Docker、编译、源码分支协调；只在必要时提供安全密钥/预算/私史导入/平台外发和生产切换授权，手机原生 APK 升级时由用户确认安装。

**最终交付必须包含**：

- 唯一最终版本的源码分支、提交与变更对照、实际完成/未完成能力矩阵；
- 自建完整 Docker 镜像及校验包、Core 源码、V4 Web、Android APK、版本兼容与签名说明；
- 可执行 `deploy.sh` / preflight / rollback / error codes 和精确路径说明；
- 现有正式 Subject 的原地升级方法，明确不会重新 Genesis、不会覆盖 Store；
- 真实 Provider/记忆/自主活动/B站/QQ/技能/语音/设备等闭环的证据；
- 与现有 AstrBot 的用户体验对照：哪些已追平、哪些已形成优势、哪些因事实限制还没有超越；
- 真正必须用户最终确认的少量动作，合并成一次明确申请。

**禁止最终只提交文档、只有漂亮前端、只有离线测试、只有 Docker 端口 403 或只有“未来待接”的能力清单，却称为全面交付成功。**

不要为加快交付而删除唯一记忆、提前停掉唯一 QQ 通道、把用户密钥写入包、跳过授权或新增第二主体。除这些不可替代的权限和事实边界外，不要制造假设性的阻塞。

### 最后一句验收原则

> **新版不是“能运行的奈奈工程”，而是“奈奈真正开始长期生活”：她会交流、会记得、会主动探索、会因经历改变判断、会学习和使用新能力；她仍是同一个奈奈，并且用户只需手机就能接触到她。**

> **一条长期任务，全面完善，一次综合发行，后续持续增量升级。**
