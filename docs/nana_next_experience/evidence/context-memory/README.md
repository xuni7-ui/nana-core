# Long-lived memory / context measurements

Development data only. Original ContinuityStore/MemoryService APIs created synthetic sources and memories, without direct row seeding, external accounts, copied private history or provider calls. No production change or live FAISS binding is claimed.

Implemented: (1) self-frame SELF filtering before the candidate bound, fixing omission when more than128 higher-ranked non-SELF records belong to the Subject; (2) rebuildable physical lookups for source binding, deferred FK checks and lexical terms; (3) rare-term ranking for large eligible sets with original ranking semantics. Dense terms and small scopes retain the old query plan. The first naive aggregate join regressed and was rejected. No plaintext query-result cache, seven-day deletion or new memory authority.

Index compatibility: business tables and schema version remain unchanged. Under the original exclusive Store lock, known physical indexes are ensured on open. Official SubjectPackage export strips only exact registered index definitions from its isolated backup; unknown/substituted definitions still fail schema validation. Original live DB and events are not rewritten by export. Import recreates the physical indexes on the new host. Package/withdrawal/original dialogue tests passed. A tampered index definition is explicitly rejected. Existing stopped-upgrade/backup/rollback policy remains required; no active-plan downgrade was qualified.

Evidence: 1k and10k baseline/candidate SQL samples (21 warm repetitions),100k and200k SQL samples, and alternating same-Store public retrieval/context comparisons (9 pairs). SQL ranking equality is not semantic generalization. Benchmark includes English keyword fixtures and source/entity filtering; it does not prove Chinese semantic retrieval or human naturalness. A bounded top128 list cannot recall all1333 relevant records at once: report recall@128 separately from precision@128, and measure later question-specific retrieval before claiming long-term recall.

Initial baseline corpus creation at10k took126.49s. Final fresh10k fixture creation with the lookups took8.11s, with different concurrent host load and opaque IDs; this is an indicative development-write result, not a general throughput guarantee. Larger corpus creation was interrupted/resumed during index investigation; its wall_seconds are per segment and must not be described as a complete fresh-build duration. All records remained in the same disposable original Store; no partial corpus was silently reset.

Context counter remains explicitly UTF8_BYTE_ESTIMATE_v1_NOT_PROVIDER_TOKENIZER. Provider-reported tokens/cost, semantic error rate, live authoritative Store/vector mapping and real cross-day outcomes are NOT_RUN/unknown. No fee or naturalness savings are inferred. Existing S8 retains independent evaluation and rollback; developer benchmark changes are not Nana's self-learning and do not auto-adopt a production learning policy.

Reproduce from repository with a qualified Python: `python -m tools.nana_next_experience.memory_scale_compare --root <fresh-private-synthetic-dir> --count 200000`, then `python -m tools.nana_next_experience.retrieval_compare --root <that-dir>`. The latter compares the original ranking strategy against the current strategy using the same corrected self-frame and live in-process Store. `live_memory_inventory --store <explicit-owned-live-db>` only reads counts/identity/index metadata; it does not inspect secret/private payloads or assert vector-store integration. Run it only through the existing host/migration authority, never against a guessed production path.

Validation scope: focused original-memory/context/portable/dialogue suite28 passed; related H1/provider/affective suite98 passed. With explicit absolute PYTHONPATH selecting this checkout, both follow-up SIGKILL tests passed. The interrupted run is retained as an environment diagnostic, not a full regression result.
