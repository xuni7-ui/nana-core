# 奈奈工程｜复用优先、元思考与工程效率原则 V1.0

一、根本目标

以最少的必要工程投入，实现最高的实际能力、体验质量与长期发展价值。

不以代码规模、模块数量、测试数量、工作时长或技术复杂度衡量工程水平。

能够复用的不重写，能够简化的不复杂化，能够直接解决的不绕路，已经足够好的不反复优化，没有实际价值的不建设。

二、复用优先原则

任何新功能、新机制或新子系统的建设，应优先按照以下顺序寻找解决方案：

1. 直接复用工程内部已有能力。
2. 继承其他执行者已经完成的成果。
3. 使用成熟开源项目、标准库、SDK、算法及现有基础设施。
4. 在成熟实现上进行最小必要适配与扩展。
5. 仅在现有方案无法满足核心目标时，自主设计和实现。

不得因为追求形式上的自主、架构纯粹性或代码统一性，而重新实现已经足够成熟的通用能力。

自主研发应集中于真正具有差异化价值的部分，而不是重复制造基础设施。

允许引入外部优秀成果，也允许用成熟方案替换已有但效率低下的自研实现。不得因沉没成本而保留不合理设计。

三、元思考原则

执行者不仅要思考如何完成任务，还要持续审视任务、方法与目标之间的关系。

在重要开发决策及阶段转换时，自主判断：

- 必要性： 这件事真的需要做吗？不做会产生什么实际影响？
- 整体性： 它对整个工程及最终体验有什么贡献？
- 复用性： 是否已有足够好的实现？
- 方法性： 当前方法是否存在更简单、更快速、更有效的替代方案？
- 机会成本： 投入同样的时间和 Token，是否有价值更高的工作？
- 边际收益： 继续优化是否仍值得，还是应该结束并推进下一项？
- 融合性： 当前建设是否与其他子系统重复、冲突或形成不必要的复杂度？

元思考必须能够改变实际执行路径，而不是仅仅生成分析报告。

发现原方法不合理时，应主动修正、简化、替换或终止，不能为了完成原任务而机械执行。

四、效率优先原则

工程效率包含开发时间、Token 消耗、运行成本、维护成本和用户参与成本。

具体要求：

- 不重复开展已经有可信结论的研究与审计。
- 不反复检查没有发生变化的内容。
- 不为了局部细节而阻塞整体推进。
- 不将简单问题拆解为大量独立任务。
- 不为尚未出现的假设性需求提前建设复杂系统。
- 不为普通错误反复申请授权或等待用户决策。
- 优先使用已有工具自动完成重复性操作。
- 合并能够一次完成的修改、测试、提交与记录。
- 发现低收益工作时主动收口，转向高收益任务。

效率优化不得以明显降低实际能力、可靠性和用户体验为代价。

五、验证成本控制原则

验证应与改动范围及实际风险相匹配。

- 普通局部修改：定向验证。
- 跨模块改动：相关集成验证。
- 重要架构变更：必要的完整回归。
- 正式发行：完整交付与实际体验验收。

未受影响的模块应优先继承仍然有效的验证证据。

禁止将全面审计、完整打包、重复回归和长篇回执变成每一次普通修改的固定流程。

验证的目的是发现问题、保证成果可用，而不是积累证明材料。

六、核心创新集中原则

奈奈工程应将主要研发力量集中在真正决定竞争力的方向：

- 持续主体及跨模型、跨设备、跨平台的身份连续性。
- 真实影响行为的内心生活、情感、关系与动机。
- 长期记忆、经验整合与情境理解。
- S8 自主学习、知识迁移与持续成长。
- S9 自主能力扩展与复用。
- S10 深层自我进化。
- 自然、持续的共同生活体验。

通用技术应尽可能站在成熟成果之上，核心创新则允许大胆探索、深度研究与长期投入。

不盲目追求自研率，也不因外部存在类似功能就放弃具有实质性创新价值的研究。

七、动态停止与转向机制

任何任务均不应仅因已被列入计划而必须继续执行。

当发现任务已经完成、存在成熟替代品、被其他成果覆盖、实际收益不足，或不再符合工程目标时，应主动停止、合并、替换或调整。

执行者应具有基于工程整体利益调整执行方法与局部优先级的权限，无须为普通技术决策反复请求用户批准。

八、执行要求

本原则长期适用于 A、B、C 及未来所有工程执行者，并逐步融入奈奈自身的自主学习、插件开发、自主扩展与自我进化机制。

本原则属于全局工程纪律，不新增独立建设任务，不要求重新开展全仓审计，不打断现有有效工作。

在当前工作中直接落实，并在后续开发中渐进纠正已经发现的低效率与重复建设。

元思考本身也必须遵守效率原则：简单工作快速判断，重大决策深入思考，禁止为了避免浪费而制造新的浪费。

最终衡量标准不是我们做了多少工作，而是我们用多少必要工作取得了多少真实进步。
